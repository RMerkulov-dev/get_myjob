# Skill Dossier

Трекер требований из вакансий **Project Manager / Business Analyst**.

Вставляешь описание вакансии → ИИ через OpenRouter разбирает её на требования и технологии → они попадают в базу Supabase без дублей. Каждое требование можно оценить по шкале 0–5 и отметить выученным.

Дальше по каждому требованию есть **режим обучения**: ИИ ищет свежий материал в сети и показывает, как об этом спросит рекрутер, потом объясняет суть, а в конце даёт квиз из 5 вопросов. Плюс **отчёт** с метриками прогресса и топом востребованных технологий и **чат** с ИИ, который видит всю твою базу.

Отдельная вкладка **CV Check** проверяет твои документы: загружаешь резюме в PDF или DOCX (или вставляешь текст) и получаешь правки по пунктам — что не так, точная цитата из документа и готовая формулировка на замену. Плюс отдельная **ATS-оценка** со списком, что поправить, чтобы пройти автоматический отбор. Четыре режима: резюме, сопроводительное письмо и профиль LinkedIn оцениваются сами по себе, по чек-листу. Последний режим — **резюме ↔ вакансия**: два окна, в одном твоё резюме, в другом вставленный текст объявления, и модель сверяет их требование за требованием.

Вкладка **Планер** — календарь ритма поиска: на каждый день ставится план и отмечается факт по пяти метрикам (посты в LinkedIn, свои отклики, ответы компаний, собеседования, пройденные этапы), а посты ведутся карточками со статусом от идеи до публикации. Сверху — цели месяца и конверсия воронки. Всё лежит в Supabase, а не в браузере.

Интерфейс на английском и украинском, светлая и тёмная темы.

React + Vite. Локально браузер общается с Supabase и OpenRouter напрямую; на проде запросы к ИИ идут через serverless-функцию Vercel, чтобы ключ не попадал в браузер.

## Быстрый старт

### 1. База данных

1. Создай проект на [supabase.com/dashboard](https://supabase.com/dashboard) (бесплатного тарифа хватит).
2. Открой **SQL Editor → New query**, вставь целиком содержимое [`supabase/schema.sql`](supabase/schema.sql) и нажми **Run**.
3. Зайди в **Project Settings → API** и скопируй `Project URL` и ключ `anon public`.

### 2. Ключ OpenRouter

Получи ключ на [openrouter.ai/keys](https://openrouter.ai/keys) и положи на баланс небольшую сумму. Сразу выстави там лимит трат — это единственная защита от неожиданного счёта. О ценах см. раздел [«Сколько это стоит»](#сколько-это-стоит).

### 3. Переменные окружения

```bash
cp .env.example .env
```

Заполни `.env`:

```
VITE_SUPABASE_URL=https://xxxx.supabase.co
VITE_SUPABASE_ANON_KEY=eyJhbGciOi...
VITE_OPENROUTER_API_KEY=sk-or-v1-...
VITE_OPENROUTER_MODEL=anthropic/claude-sonnet-4.5
```

Настроек в интерфейсе нет: ключ и модель читаются только из окружения.

### 4. Запуск

```bash
npm install
npm run dev
```

Vite читает `.env` только при старте — после правки файла перезапусти сервер.

При первом запуске приложение попросит войти по email и паролю или создать аккаунт — регистрация прямо в интерфейсе.

## Деплой на Vercel

Ключи не должны попасть в браузер, поэтому на проде запросы к ИИ идут через серверную функцию `api/ai/chat.js`, а данные закрыты политиками Supabase. Порядок такой:

**1. Переменные окружения** (Project Settings → Environment Variables):

| Переменная | Значение |
|---|---|
| `VITE_SUPABASE_URL` | тот же Project URL |
| `VITE_SUPABASE_ANON_KEY` | тот же anon-ключ |
| `OPENROUTER_API_KEY` | ключ OpenRouter — **без префикса `VITE_`** |

`VITE_OPENROUTER_API_KEY` на Vercel добавлять нельзя: всё с этим префиксом Vite вшивает в собранный JS открытым текстом. `OPENROUTER_API_KEY` читает только серверная функция.

**2. Деплой.** Vercel сам определит Vite: сборка `npm run build`, каталог `dist`, функции из `api/` подключаются автоматически. `vercel.json` не нужен. Настраивать `Site URL` и `Redirect URLs` в Supabase не требуется — вход по паролю не использует ссылки из писем.

## Несколько пользователей

У каждого своя карта навыков, свои вакансии и своя история чата. Никто не видит данные другого — это гарантируют политики базы, а не интерфейс.

Регистрация открытая: человек заходит по ссылке, жмёт «Create account», вводит email и пароль и сразу попадает в своё пустое досье.

**Настройки в Supabase → Authentication → Providers → Email:**

- **Allow new users to sign up** → **on** (иначе регистрация вернёт ошибку);
- **Confirm email** → **off**. Это важно: со включённым подтверждением Supabase отправляет письмо на каждую регистрацию, а встроенный SMTP отдаёт лишь пару писем в час — на третьем человеке регистрация встанет. С выключенным подтверждением аккаунт создаётся мгновенно и без писем.

Если подтверждение всё же нужно, подключи свой SMTP (Resend, Brevo, Postmark) в **Authentication → SMTP Settings** — тогда лимит определяется провайдером, а не Supabase.

**Задать пароль существующему аккаунту** (например, себе, если раньше входил по ссылке из письма) — SQL Editor:

```sql
update auth.users
   set encrypted_password = crypt('новый-пароль', gen_salt('bf')),
       email_confirmed_at = coalesce(email_confirmed_at, now())
 where email = 'ты@example.com';
```

⚠️ **Не удаляй пользователя после прогона схемы**: строки привязаны к нему через `on delete cascade`, вместе с аккаунтом уйдут все его требования и вакансии. Пароль меняй запросом выше, а не пересозданием аккаунта.

**Ограничь расход на ИИ.** Все работают через один твой ключ OpenRouter, а регистрация открытая — значит любой зарегистрировавшийся тратит твой баланс. Выставь на ключе лимит трат в настройках OpenRouter: это единственная реальная защита от неожиданного счёта. Самый дорогой запрос в приложении — режим обучения с веб-поиском.

### Что именно защищено

- **Ключ OpenRouter** живёт только в переменных Vercel и в браузер не попадает. `api/ai/chat.js` пропускает запрос лишь при валидной сессии Supabase, так что анонимно ключом воспользоваться нельзя. Ограничение расходов — лимит на самом ключе (см. выше).
- **Данные** закрыты RLS: политика `user_id = auth.uid()` на каждой таблице. Анонимный доступ закрыт полностью — зная URL и anon-ключ, посторонний не прочитает и не удалит ни строки. Связки «вакансия ↔ требование» дополнительно проверяют, что и вакансия, и требование принадлежат тому же пользователю.
- Уникальность требования — в пределах аккаунта (`unique (user_id, slug)`), поэтому «Jira» может быть у каждого своя, а внутри одного аккаунта дубля не возникнет.
- Локально `npm run dev` продолжает ходить в OpenRouter напрямую по ключу из `.env`, поэтому Vercel CLI для разработки не нужен.

## Как этим пользоваться

**Импорт.** Выбери позицию (`PM`, `BA` или `PM/BA`), вставь описание вакансии целиком и нажми «Разобрать с ИИ». Появится список найденных требований: новые помечены чёрным бейджем `новое`, уже известные — пунктиром и подписью «в базе · N-я вакансия». Лишнее можно снять галочкой, новым — сразу поставить свой уровень. Кнопка сохранения показывает, сколько записей реально добавится.

Выбор позиции влияет на теги требований: `PM/BA` проставляет оба тега, и потом можно фильтровать карту навыков отдельно по PM и по BA.

**Навыки.** Пять сегментов = уровень знания (0 — не знаю, 5 — могу учить других). Галочка «Выучено» — отдельный флаг: технология может быть выучена на уровне 3 и этого достаточно. Иконка документа на карточке открывает заметку (куда сложить ссылку на курс).

Сортировка «По приоритету» считает вес: `обязательное (+2) + частота упоминаний (×0.5) − твой уровень (×0.6) − выученное (−5)`. Сверху оказывается то, что чаще всего требуют и что ты хуже всего знаешь.

**Обучение.** Кнопка с шапочкой выпускника на карточке открывает попап. Сразу грузится только объяснение сути — оно стримится, поэтому текст виден почти мгновенно. Вопросы рекрутера (что спросят, что проверяют, как отвечать) и квиз из 5 вопросов запрашиваются кнопками: каждая часть — отдельный запрос к модели, и платить за них стоит только когда они нужны. Ответил на 4 из 5 — можно сразу отметить требование выученным. Всё загруженное кэшируется в браузере по требованию и языку, «Regenerate» обновляет то, что уже открыто.

Веб-поиск (`plugins: [{ id: 'web' }]`) по умолчанию выключен — он тарифуется отдельно и заметно медленнее. Кнопка «Add web sources» в блоке объяснения перегенерирует текст с живым поиском и списком источников. Если модель не поддерживает плагины, запрос автоматически повторяется без поиска.

**CV Check.** Четыре режима переключаются сегментами в шапке: резюме, сопроводительное письмо, LinkedIn и «резюме ↔ вакансия». У каждого свой независимый черновик — текст, критерии, язык ответа и последний разбор хранятся в `localStorage` отдельно, поэтому переключение вкладок и перезагрузка страницы ничего не стирают.

Первые три режима ничего ни с чем не сравнивают: документ оценивается сам по себе, строго по чек-листу. Сравнение — отдельная работа, и живёт оно только в последнем режиме, чтобы не было непонятно, с чем именно тебя только что сверили.

PDF разбирается прямо в браузере: `pdfjs-dist` подгружается динамически (отдельный чанк ~420 КБ) только когда файл реально уронили в форму, воркер отдаётся Vite как обычный ассет.

Текст собирается по координатам, а не в порядке потока PDF ([pdfText.js](src/lib/pdfText.js)). Это не придирка: дизайнерские шаблоны резюме почти всегда двухколоночные, и pdf.js отдаёт фрагменты в порядке отрисовки — сначала заголовки сайдбара, потом вперемешку их содержимое и основная колонка. Модель читала кашу. Поэтому на каждой странице ищется вертикальная полоса, которую не пересекает ни один фрагмент (единичные сквозные элементы допустимы — шапка резюме почти всегда на всю ширину и выносится отдельно), колонки читаются сверху вниз, строки собираются по общей `y`, а пробел внутри строки ставится только там, где между фрагментами реальный зазор. Отдельно схлопывается разрядка: дизайнеры сохраняют заголовки как «E D U C A T I O N», и без этого они не опознаются ни моделью, ни поиском по ключевым словам. Если в PDF нет текстового слоя (скан или картинка), приложение так и говорит и предлагает вставить текст руками. DOCX читается своим кодом без библиотек ([docx.js](src/lib/docx.js)): `.docx` — это zip, а браузер умеет и распаковку (`DecompressionStream('deflate-raw')`), и разбор XML (`DOMParser`), так что mammoth с его сотнями килобайт не нужен — нам нужен текст с абзацами и списками, а не стили. Разбирается центральный каталог zip, а не локальные заголовки: Word и Google Docs пишут файл потоком, и размеры в локальных заголовках у них нулевые. Пункты списков (`w:numPr`) помечаются дефисом, строки таблиц собираются в строку через « · », колонтитулы читаются тоже — в резюме там часто лежат имя и контакты. Старый бинарный `.doc` не поддерживается, и об этом говорится прямо.

Кроме PDF и DOCX принимаются `.txt` и `.md`; извлечённый текст можно править перед проверкой.

«Критерии проверки» — это чек-лист, по которому отвечает модель. По умолчанию подставляется свой для каждого типа документа и на языке ответа (EN / UA / RU); его можно править или заменить целиком своим списком, «Сбросить» возвращает типовой. Одна строка = один проверяемый пункт.

Язык ответа выбирается отдельно от языка интерфейса: анализ приходит на выбранном языке, а готовые формулировки — на языке самого документа, поэтому резюме на английском правится по-английски, даже если разбор читаешь по-русски.

Галочка «проверять под мою базу» есть только в режиме сравнения и добавляет к запросу выжимку по навыкам: самые частые требования с уровнями и что уже выучено. Само объявление уходит в запрос дословно, поэтому пересказывать его выжимкой незачем — база лишь дополняет её твоей самооценкой.

**Резюме ↔ вакансия** — единственный режим со сравнением, и в нём два поля: сверху резюме (можно взять одной кнопкой с первой вкладки), ниже текст объявления. Объявление либо вставляется руками, либо выбирается из уже разобранных вакансий — тогда в поле подставляется её исходный текст. Оценка здесь = соответствие: что резюме реально подтверждает против обязательных требований этого объявления, а не «в целом по рынку». Дальше — что отсеет заявку на скрининге, какие красные флаги в объявлении (три роли в одной, неоплачиваемое тестовое, ни слова о команде), чего оно не говорит вслух и о чём придётся спросить. В поле «чем это закрыть» вместо правки приходит готовая фраза для резюме, письма или ответа на интервью. ATS-оценка в этом режиме считается против конкретного объявления: пропущенные ключевые слова берутся из его же формулировок.

**Метрики.** Кроме общей оценки разбор раскладывается на пять осей — у каждого типа документа свои (для резюме: покрытие ключевых слов, достижения и цифры, структура и читаемость, качество формулировок, соответствие целевой роли; для вакансии: покрытие обязательных требований, ясность роли, прозрачность условий, отсутствие красных флагов, потенциал роста). Каждая ось — число из 100 полосой и строка о том, что дало эту цифру, со ссылкой на факт из документа. Везде «больше — лучше», чтобы полосы читались одинаково.

**ATS-оценка** считается отдельным числом рядом с общей: насколько дословно в документе присутствуют термины целевых вакансий и насколько вёрстка читается машиной. Под ней — что конкретно поправить: отсутствующие ключевые слова (кликом копируются по одному) и 3–6 правок по секциям, датам и заголовкам. У вакансии этой метрики нет — объявление работодателя через ATS не проходит, и приложение это гасит само, не полагаясь на модель.

Результат: оценка 0–100, вердикт, разбор по метрикам, что уже работает, правки по пунктам (важность, проблема, цитата «сейчас», готовая замена с кнопкой копирования), чего не хватает совсем и что делать дальше. «Копировать весь разбор» отдаёт всё это markdown-ом. Ответ — один стриминговый JSON-запрос: стрим нужен, чтобы функция на Vercel не упиралась в таймаут до первого байта.

**Отчёт.** KPI прогресса, топ технологий по частоте упоминаний, распределение самооценки по уровням, срез по категориям, сравнение готовности к PM и BA, приоритетный список пробелов и динамика по месяцам. Все графики — одна серия на нейтральной дорожке: величину несёт длина полосы, а идентичность подписана текстом, поэтому диаграммы читаются и при цветовой слепоте.

**Планер.** Календарь на месяц: неделя начинается с понедельника, сегодняшний день обведён акцентом, в правой колонке — итог за неделю. Клик по дню открывает редактор: план и факт по пяти метрикам (посты в LinkedIn, свои отклики, ответы компаний, собеседования, пройденные этапы), заметка на день и карточки постов — заголовок, тема, статус (идея → черновик → запланировано → опубликовано), ссылка и черновик тезисов.

В клетке видно только то, что заполнено: `ПО 1/2` — метрика, факт и план. Рамка зелёная, когда план на день закрыт, янтарная — когда сделано частично. Пустой день в базе не создаётся, а если стереть все цифры и заметку — строка удаляется: в таблице лежат только те дни, которые ты действительно вёл.

Кнопка «Цели месяца» задаёт верхнюю планку по каждой метрике. Карточки под календарём считают факт против цели, а если цели нет — против суммы дневных планов; ниже — конверсия воронки (сколько откликов на одну ответившую компанию, сколько ответов на одно собеседование) и сколько постов из запланированных вышло.

**Чат.** Модель получает системный промпт и полный дамп базы: названия, категории, уровни, флаги, частоты, позиции и заметки. Ответы стримятся, история хранится в таблице `chat_messages`.

## Сколько это стоит

Приложение использует три модели: дорогая нужна там, где важен связный текст и точность извлечения, короткие структурированные ответы считает самая дешёвая, а разбор документов — отдельная сильная. Задаются переменными `VITE_OPENROUTER_MODEL`, `VITE_OPENROUTER_MODEL_FAST` и `VITE_OPENROUTER_MODEL_REVIEW`.

CV Check по умолчанию идёт на `anthropic/claude-sonnet-5`: там задача не «извлечь факты», а отредактировать текст, который человек отправит работодателю, и на этом разрыв между дешёвой и сильной моделью самый заметный.

Один разбор резюме на две страницы — **≈ 9 ¢**, и почти всё это выход: замеренный запрос — 4 100 токенов входа и 8 300 выхода, из которых **4 750 ушло в reasoning**. Отсюда два следствия. Первое: reasoning тарифицируется как выход, поэтому дешёвой такая проверка не будет. Второе: reasoning расходует тот же `max_tokens`, поэтому лимит стоит 16 000 — на 8 000 разбор обрывался ещё в рассуждениях, и наверх приходил пустой ответ. Проверка документов делается десяток раз, а не на каждую вакансию, так что на общей стоимости это почти не видно.

Цены OpenRouter за 1M токенов и стоимость одного урока (три запроса, ~4000 токенов входа и 2500 выхода):

| Модель | Вход | Выход | Урок |
|---|---|---|---|
| `anthropic/claude-sonnet-4.5` | $3.00 | $15.00 | ≈ 5.0 ¢ |
| `anthropic/claude-haiku-4.5` | $1.00 | $5.00 | ≈ 1.7 ¢ |
| `google/gemini-2.5-flash` ← по умолчанию | $0.30 | $2.50 | ≈ 0.7 ¢ |
| `openai/gpt-4o-mini` | $0.15 | $0.60 | ≈ 0.2 ¢ |
| `google/gemini-2.5-flash-lite` ← для JSON | $0.10 | $0.40 | ≈ 0.1 ¢ |

Что ещё влияет на счёт:

- **Веб-поиск тарифуется отдельно** — около $4 за 1000 результатов, то есть ~0.8 ¢ за запрос. Поэтому он больше не включается автоматически: в блоке объяснения есть кнопка «Add web sources», которая перегенерирует текст с живым поиском. Без неё модель отвечает по своим знаниям — для устоявшихся тем вроде Kanban или BPMN этого достаточно.
- **По кнопке, а не сразу.** При открытии карточки идёт один запрос — на объяснение. Вопросы рекрутера и квиз генерируются только если нажать соответствующую кнопку, так что типичный просмотр стоит втрое дешевле полного урока.
- **Готовый урок кэшируется** в браузере по требованию и языку: повторное открытие карточки бесплатно. Платит только первая генерация и «Regenerate».
- **Длина ответов ограничена** через `max_tokens`, а промпты просят лаконичность — выход дороже входа в 4–8 раз, поэтому экономия именно на нём.
- **Разбор вакансии** отправляет не больше 14 000 символов текста и до 180 известных названий требований, а из ответа убрано всё, что приложение умеет вычислить само.

Если качество дешёвой модели где-то не устроит, верни на этот участок платную: достаточно поменять переменную окружения и сделать redeploy.

## Как работает дедупликация

Требование из вакансии проходит несколько шагов, прежде чем стать записью в базе:

1. **Нормализация** — убираются регистр, `ё`, кавычки, содержимое скобок, пунктуация; срезаются шумные обёртки («опыт работы с», «уверенное владение», «обязательно»), уровни (`B2`, `senior`) и хвосты-пустышки («методологии», «домен»).
2. **Кириллические двойники** — «МS Project» с русской `М` превращается в латинский `MS Project`.
3. **Лемматизация** — «методологиями» и «методологии» сводятся к одной основе.
4. **Карта синонимов** — «Джира», «JIRA Software», «опыт работы с Jira» → `jira`; «гибкие методологии разработки» → `agile`; «управление стейкхолдерами» → `stakeholder-management`.
5. **Сверка с базой** — по ключу, по алиасам и по «сжатой» форме без символов (`CI/CD` = `cicd`).
6. **Подсказка модели** — в промпт передаётся список уже известных названий с требованием переиспользовать их символ в символ.

Уникальность гарантируется на уровне БД: `skills.slug` — `unique`, вставка идёт через `upsert(onConflict: 'slug')`. Отображаемое имя новой записи приводится к канону (`Гибкие методологии разработки` → `Agile`), а исходная формулировка из вакансии сохраняется в `aliases` — так следующие совпадения находятся ещё надёжнее.

Если дубль всё-таки проскочил — удали лишнюю карточку, её формулировка подтянется алиасом при следующем импорте.

## Структура

```
api/
  _guard.js        проверка сессии Supabase и списка разрешённых email
  ai/chat.js       прокси к OpenRouter со стримингом (Edge Function)
src/
  lib/
    normalize.js   нормализация названий, синонимы, поиск существующего требования
    db.js          все запросы к Supabase + логика «добавить только новое»
    openrouter.js  разбор вакансии, уроки, разбор документов; сам решает — напрямую или через /api/ai
    pdf.js         извлечение текста из PDF в браузере (pdfjs-dist, ленивый импорт)
    pdfText.js     сборка текста по координатам: колонки, строки, разрядка
    docx.js        чтение .docx без зависимостей: zip + XML силами браузера
    checklists.js  чек-листы CV Check по умолчанию: 3 типа документа × 3 языка
    planner.js     метрики планера, календарная сетка, суммы за месяц и неделю
    markdown.jsx   минимальный рендерер ответов ИИ (без зависимостей)
    theme.js       светлая / тёмная / как в системе
    settings.js    ключ и модель из окружения
  i18n/            en.js, uk.js и провайдер с плюрализацией
  components/      экраны: вход, импорт, навыки, CV Check, отчёт, вакансии, планер, чат + попапы обучения и дня
  styles.css       дизайн-система целиком, включая обе темы
supabase/schema.sql
```

Язык и тема переключаются в правом верхнем углу. Тема: авто (по настройкам ОС), светлая, тёмная — в режиме «авто» приложение реагирует на смену темы в системе на ходу. Язык влияет и на промпты: описания, объяснения и квизы ИИ генерирует на выбранном языке, а сами промпты всегда на английском — так модели стабильнее следуют инструкциям.

Таблицы: `skills` (справочник требований), `vacancies` (исходники), `vacancy_skills` (связка с цитатой и важностью), `chat_messages`, `plan_days` (план и факт по дням), `linkedin_posts` (карточки постов), `plan_goals` (цели месяца). У каждой есть `user_id` со значением по умолчанию `auth.uid()`, поэтому клиент про него ничего не знает. Счётчик `skills.mentions` пересчитывается триггером — при удалении вакансии он уменьшается сам.

## Обновление схемы

`supabase/schema.sql` идемпотентный — его можно прогонять повторно на живой базе. Если база создавалась в однопользовательской версии, скрипт сам добавит `user_id`, привяжет существующие строки к самому раннему аккаунту (это владелец базы), заменит глобальную уникальность `slug` на уникальность в пределах пользователя и обновит политики. Данные не теряются.
