# Skill Dossier

Трекер требований из вакансий **Project Manager / Business Analyst**.

Вставляешь описание вакансии → ИИ через OpenRouter разбирает её на требования и технологии → они попадают в базу Supabase без дублей. Каждое требование можно оценить по шкале 0–5 и отметить выученным.

Дальше по каждому требованию есть **режим обучения**: ИИ ищет свежий материал в сети и показывает, как об этом спросит рекрутер, потом объясняет суть, а в конце даёт квиз из 5 вопросов. Плюс **отчёт** с метриками прогресса и топом востребованных технологий и **чат** с ИИ, который видит всю твою базу.

Интерфейс на английском и украинском, светлая и тёмная темы.

React + Vite. Локально браузер общается с Supabase и OpenRouter напрямую; на проде запросы к ИИ идут через serverless-функцию Vercel, чтобы ключ не попадал в браузер.

## Быстрый старт

### 1. База данных

1. Создай проект на [supabase.com/dashboard](https://supabase.com/dashboard) (бесплатного тарифа хватит).
2. Открой **SQL Editor → New query**, вставь целиком содержимое [`supabase/schema.sql`](supabase/schema.sql) и нажми **Run**.
3. Зайди в **Project Settings → API** и скопируй `Project URL` и ключ `anon public`.

### 2. Ключ OpenRouter

Получи ключ на [openrouter.ai/keys](https://openrouter.ai/keys) и положи на баланс небольшую сумму — разбор одной вакансии стоит меньше цента.

### 3. Переменные окружения

```bash
cp .env.example .env
```

Заполни `.env`:

```
VITE_SUPABASE_URL=https://xxxx.supabase.co
VITE_SUPABASE_ANON_KEY=eyJhbGciOi...
VITE_OPENROUTER_API_KEY=sk-or-v1-...
VITE_OPENROUTER_MODEL=anthropic/claude-sonnet-4.5
```

Настроек в интерфейсе нет: ключ и модель читаются только из окружения.

### 4. Запуск

```bash
npm install
npm run dev
```

Vite читает `.env` только при старте — после правки файла перезапусти сервер.

При первом запуске приложение попросит войти: вводишь email → получаешь ссылку на почту → открываешь её в этом же браузере. Email должен совпадать с тем, что указан в функции `is_owner()` в `schema.sql`, иначе база не отдаст ни строки.

## Деплой на Vercel

Ключи не должны попасть в браузер, поэтому на проде запросы к ИИ идут через серверную функцию `api/ai/chat.js`, а данные закрыты политиками Supabase. Порядок такой:

**1. Переменные окружения** (Project Settings → Environment Variables):

| Переменная | Значение |
|---|---|
| `VITE_SUPABASE_URL` | тот же Project URL |
| `VITE_SUPABASE_ANON_KEY` | тот же anon-ключ |
| `OPENROUTER_API_KEY` | ключ OpenRouter — **без префикса `VITE_`** |
| `ALLOWED_EMAILS` | твой email (через запятую, если нужно несколько) |

`VITE_OPENROUTER_API_KEY` на Vercel добавлять нельзя: всё с этим префиксом Vite вшивает в собранный JS открытым текстом. `OPENROUTER_API_KEY` читает только серверная функция.

**2. Redirect URL в Supabase** (Authentication → URL Configuration): в `Site URL` поставь адрес продакшена, а в `Redirect URLs` добавь и его, и `http://localhost:5173` — иначе ссылка из письма будет уводить не туда.

**3. Владелец базы.** В `supabase/schema.sql` в функции `is_owner()` перечислены разрешённые email — оставь свой, лишние удали. Прогони схему заново: она идемпотентна и просто обновит политики.

**4. Деплой.** Vercel сам определит Vite: сборка `npm run build`, каталог `dist`, функции из `api/` подключаются автоматически. `vercel.json` не нужен.

### Что именно защищено

- **Ключ OpenRouter** живёт только в переменных Vercel. `api/ai/chat.js` перед проксированием проверяет токен сессии Supabase и сверяет email со списком `ALLOWED_EMAILS`, так что чужой человек не сможет тратить твой баланс даже открыв сайт.
- **Данные** закрыты RLS: политики разрешают операции только роли `authenticated` и только при совпадении email с `is_owner()`. Анонимный доступ закрыт полностью — зная URL и anon-ключ, посторонний не прочитает и не удалит ни строки.
- Локально `npm run dev` продолжает ходить в OpenRouter напрямую по ключу из `.env`, поэтому Vercel CLI для разработки не нужен.

## Как этим пользоваться

**Импорт.** Выбери позицию (`PM`, `BA` или `PM/BA`), вставь описание вакансии целиком и нажми «Разобрать с ИИ». Появится список найденных требований: новые помечены чёрным бейджем `новое`, уже известные — пунктиром и подписью «в базе · N-я вакансия». Лишнее можно снять галочкой, новым — сразу поставить свой уровень. Кнопка сохранения показывает, сколько записей реально добавится.

Выбор позиции влияет на теги требований: `PM/BA` проставляет оба тега, и потом можно фильтровать карту навыков отдельно по PM и по BA.

**Навыки.** Пять сегментов = уровень знания (0 — не знаю, 5 — могу учить других). Галочка «Выучено» — отдельный флаг: технология может быть выучена на уровне 3 и этого достаточно. Иконка документа на карточке открывает заметку (куда сложить ссылку на курс).

Сортировка «По приоритету» считает вес: `обязательное (+2) + частота упоминаний (×0.5) − твой уровень (×0.6) − выученное (−5)`. Сверху оказывается то, что чаще всего требуют и что ты хуже всего знаешь.

**Обучение.** Кнопка с шапочкой выпускника на карточке открывает попап: сначала 3-4 вопроса, которые реально задаст рекрутер (что проверяют и как отвечать), затем объяснение сути со ссылками на источники, затем квиз. Ответил на 4 из 5 — можно сразу отметить требование выученным. Материал кэшируется в браузере по требованию и языку, кнопка «Regenerate» перегенерирует его.

Запрос идёт с включённым веб-поиском OpenRouter (`plugins: [{ id: 'web' }]`), поэтому факты и терминология свежие. Если модель не поддерживает плагины, запрос автоматически повторяется без поиска.

**Отчёт.** KPI прогресса, топ технологий по частоте упоминаний, распределение самооценки по уровням, срез по категориям, сравнение готовности к PM и BA, приоритетный список пробелов и динамика по месяцам. Все графики — одна серия на нейтральной дорожке: величину несёт длина полосы, а идентичность подписана текстом, поэтому диаграммы читаются и при цветовой слепоте.

**Чат.** Модель получает системный промпт и полный дамп базы: названия, категории, уровни, флаги, частоты, позиции и заметки. Ответы стримятся, история хранится в таблице `chat_messages`.

## Как работает дедупликация

Требование из вакансии проходит несколько шагов, прежде чем стать записью в базе:

1. **Нормализация** — убираются регистр, `ё`, кавычки, содержимое скобок, пунктуация; срезаются шумные обёртки («опыт работы с», «уверенное владение», «обязательно»), уровни (`B2`, `senior`) и хвосты-пустышки («методологии», «домен»).
2. **Кириллические двойники** — «МS Project» с русской `М` превращается в латинский `MS Project`.
3. **Лемматизация** — «методологиями» и «методологии» сводятся к одной основе.
4. **Карта синонимов** — «Джира», «JIRA Software», «опыт работы с Jira» → `jira`; «гибкие методологии разработки» → `agile`; «управление стейкхолдерами» → `stakeholder-management`.
5. **Сверка с базой** — по ключу, по алиасам и по «сжатой» форме без символов (`CI/CD` = `cicd`).
6. **Подсказка модели** — в промпт передаётся список уже известных названий с требованием переиспользовать их символ в символ.

Уникальность гарантируется на уровне БД: `skills.slug` — `unique`, вставка идёт через `upsert(onConflict: 'slug')`. Отображаемое имя новой записи приводится к канону (`Гибкие методологии разработки` → `Agile`), а исходная формулировка из вакансии сохраняется в `aliases` — так следующие совпадения находятся ещё надёжнее.

Если дубль всё-таки проскочил — удали лишнюю карточку, её формулировка подтянется алиасом при следующем импорте.

## Структура

```
api/
  _guard.js        проверка сессии Supabase и списка разрешённых email
  ai/chat.js       прокси к OpenRouter со стримингом (Edge Function)
src/
  lib/
    normalize.js   нормализация названий, синонимы, поиск существующего требования
    db.js          все запросы к Supabase + логика «добавить только новое»
    openrouter.js  разбор вакансии, стриминг чата; сам решает — напрямую или через /api/ai
    markdown.jsx   минимальный рендерер ответов ИИ (без зависимостей)
    theme.js       светлая / тёмная / как в системе
    settings.js    ключ и модель из окружения
  i18n/            en.js, uk.js и провайдер с плюрализацией
  components/      экраны: вход, импорт, навыки, отчёт, вакансии, чат + попап обучения
  styles.css       дизайн-система целиком, включая обе темы
supabase/schema.sql
```

Язык и тема переключаются в правом верхнем углу. Тема: авто (по настройкам ОС), светлая, тёмная — в режиме «авто» приложение реагирует на смену темы в системе на ходу. Язык влияет и на промпты: описания, объяснения и квизы ИИ генерирует на выбранном языке, а сами промпты всегда на английском — так модели стабильнее следуют инструкциям.

Таблицы: `skills` (справочник требований), `vacancies` (исходники), `vacancy_skills` (связка с цитатой и важностью), `chat_messages`. Счётчик `skills.mentions` пересчитывается триггером — при удалении вакансии он уменьшается сам.

## Про безопасность

Приложение однопользовательское: доступ определяется email в функции `is_owner()` (база) и переменной `ALLOWED_EMAILS` (серверная функция ИИ). Чтобы сменить владельца, поменяй email в этих двух местах.

Если однажды захочешь пускать нескольких человек с раздельными данными — понадобится колонка `user_id` в таблицах и политики вида `auth.uid() = user_id` вместо `is_owner()`; существующие строки при этом нужно будет привязать к своему `user_id`.
